# AGENTS.md

Instructions for AI coding agents working in the MPLAD-SHIELD repository.

Read this before editing anything. The rules in §2 are not style preferences —
breaking them produces a system that looks fine and is wrong.

---

## 1. What this project is

A risk-scoring layer over the MPLADS public works register. It ranks projects for
human review. It does **not** determine fraud. See `PRD.md` for the full product
definition and `ARCHITECTURE.md` for how the pieces connect.

## 2. Hard rules

### 2.1 Never hardcode a risk value in the UI

Every number the interface displays comes from `outputs/scored.json`, which the
Python engine produces. If a screen needs a figure that isn't in that file, add
it to the engine's export — do not compute it in TypeScript and do not inline a
placeholder. A demo value that survives into a submission is the single worst
failure mode for this project.

### 2.2 Never phrase output as a finding of wrongdoing

Banned in anything a user can see, and in identifiers: UI copy, exported
strings, column names, variable and function names, commit messages.

> fraud, fraudulent, corrupt, guilty, culprit, offender, scam, embezzlement,
> caught, proof, evidence of

Use instead:

> unusual pattern, requires review, flagged for inspection, deviates from peers,
> risk indicator, potential risk

The one permitted use is stating the boundary itself — a docstring or comment
saying the system does *not* establish fraud. `scoring.py` does exactly this, and
`data_gen.py` uses "fraud labels" to describe the absence of ground truth. Both
are correct; the rule targets claims, not the word.

The standing line, which must appear on the project detail screen and in every
export, is stored as `assessment` in the export and reads:

> Unusual pattern identified for human review. This score does not establish
> irregularity or fraud.

Do not reword it.

### 2.3 The score must decompose exactly

`points_cost_deviation + points_delay + ... == risk_score`, within 0.15. There is
a test asserting this (`test_score_decomposes_exactly`). If you change the
combination logic in `scoring.py`, that test must still pass. A score a reviewer
cannot see the arithmetic behind is not shippable.

### 2.4 Re-benchmark after any detector change

If you touch `detectors.py`, `features.py`, `models.py`, `scoring.py` or the caps
and thresholds in `config.py`:

```bash
python run.py --n 1200 --seed 42
python -m pytest tests/ -q
```

Report the before and after for ROC-AUC, average precision, precision@50, and
recall by irregularity type. A change that improves one detector at the cost of
another is a trade-off the human needs to see, not one to resolve silently.

### 2.5 Tunables live in config.py only

Thresholds, indicator caps, band boundaries, inadmissible categories and expected
durations belong in `mplad_shield/config.py`. Never inline a magic number in a
detector. If a value needs to vary by district or by guideline edition, it goes
in config with a comment explaining what it is and why it has that default.

### 2.6 Do not over-tune on synthetic data

The benchmark register is generated by `data_gen.py`. Pushing the metrics by
fitting the quirks of that generator is worthless and actively misleading. If a
change improves the benchmark but you cannot explain *mechanically* why it would
help on a real register, do not make it.

### 2.7 Never mix the two data modes

`python run.py` generates a labelled synthetic register into
`outputs/synthetic_benchmark/`. `python score_works.py` scores the real exports
into `outputs/`. They must never share an output directory. A payload's
`meta.data_mode` reads either `official_export` or `synthetic_benchmark`, and
that is what the dashboard banner reports. If unsure which is on screen, check
that field before anything else.

### 2.8 Never commit a real register

Real MPLADS data, extracts, or anything containing officials' names stays out of
git. `.gitignore` covers `data/`, `*.csv` outside `outputs/`, and `.env`.

## 3. Repository layout

```
mplad_shield/          Python risk engine
  config.py            domain constants, indicator caps, thresholds
  data_gen.py          synthetic register with labelled irregularities
  features.py          peer groups, robust deviation, delay, mismatch
  detectors.py         the six detectors and the rule engine
  models.py            Isolation Forest, DBSCAN, SHAP attribution
  scoring.py           combination, explanations, queue, agency rollup
  evaluate.py          ROC-AUC, average precision, precision/recall @ k
  pipeline.py          orchestration and export
run.py                 CLI entry point
tests/                 pytest suite
outputs/               generated — scored.json is the UI's input
web/                   React frontend (reads outputs/scored.json)
```

## 4. Commands

```bash
# setup
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# engine
python run.py                        # synthetic benchmark, 1200 works
python run.py --n 5000 --top 100     # larger run
python run.py --csv register.csv     # real register
python -m pytest tests/ -q           # 14 tests, must all pass

# frontend
cd web && npm install && npm run dev
```

## 5. Conventions

### Python

- Type hints on every public function. `from __future__ import annotations` at
  the top of modules using `X | None`.
- Docstrings explain **why**, not what. `features.py` explaining why median and
  MAD are used instead of mean and standard deviation is the standard to match.
  A docstring restating the function name is noise.
- Detectors return a `pd.Series` in `[0, 1]` indexed like the input. No detector
  returns raw units.
- Never mutate the input DataFrame. Copy, add columns, return.
- Prefer vectorised pandas over row loops except where building per-row
  explanation objects.

### TypeScript / React

- Function components with hooks. No class components.
- Types for the `scored.json` shape live in `web/src/types/scored.ts` and are the
  single source of truth — derive, don't duplicate.
- Risk colour is never the only signal. Every band indicator pairs colour with
  text (see `DESIGN_SYSTEM.md` §6).
- Currency formats in Indian notation: `₹1,24,18,938`, not `₹12,418,938`.

### Commits

```
engine: widen delay tolerance band to 0.25
web: show per-indicator points on project detail
docs: record benchmark after duplicate cap change
```

One concern per commit. If a commit changes detector behaviour, put the
before/after metrics in the body.

## 6. When you are unsure

Stop and ask rather than guessing, specifically about:

- Changing an indicator cap or band boundary — these shift every score in the
  system and invalidate any figure already quoted in the deck
- Adding a new detector — it changes the decomposition and needs a cap
- Anything touching the wording in §2.2
- Anything that would make the UI call a model at request time (see
  `ARCHITECTURE.md` §5 for why this is a deliberate constraint, not an oversight)

## 7. Things that look like bugs and are not

- **Works cheaper than their peers score 0 on cost.** Deliberate. Only the upper
  tail is scored; flagging savings would flood the queue.
- **Most projects score near 0 on most indicators.** Deliberate. Detectors have
  deadbands so ordinary works sit quiet; without them every record carries
  background evidence and genuinely bad works stop standing out.
- **`multivariate` is zero for ~85% of works.** Deliberate. Isolation Forest
  scores every record, so only its top 15% by rank is treated as signal.
- **Indicator caps do not sum to 1.** Deliberate. They are per-indicator ceilings
  under a noisy-OR combination, not shares of a weighted average.
